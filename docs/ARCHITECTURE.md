# Архитектура BMM v0.3

## Модули и данные

`Generator` создаёт `Page` по индексу. Страница содержит адрес, исходный текст, индекс, `source_mode`, версию генератора и для синтетического внедрения точные границы вставки. Реализованы локальный SplitMix64, контролируемое внедрение и генерация из конечной грамматики. Текст в анализаторе не исправляется.

`Analyzer::analyze_page()` возвращает `PageAnalysis`: словарные/предложенческие находки, фрагменты из последовательных предложений и `AnalysisMetrics`. Автомат Ахо — Корасик и модели после построения используются рабочими потоками только для чтения. Нормализация словаря удаляет дубли; смещения относятся к исходным байтам и записываются как полуоткрытые интервалы `[start,end)` с нуля.

`Grammar` проверяет ограниченную конечную грамматику, `NGramLanguageModel` хранит частоты и считает вероятности, `SentenceScorer` объединяет оценки для ранжирования. `PassageDiscoveryEngine` проверяет последовательность исходных предложений и вычисляет компоненты поверхностной связности. Межстраничное объединение выключено: независимые локальные страницы не задают осмысленного порядка текста.

`Scanner` управляет рабочими потоками и вызывает `Storage` из единственного записывающего потока. Ядро ничего не печатает в терминал. CLI связывает параметры, обработчики сигналов, progress callback, JSON и файловые пути. C++-интерфейс `SemanticValidator` остаётся точкой расширения; рабочий опциональный клиент Ollama вынесен в отдельную Python-команду по экспорту кандидатов.

## Ограниченное окно работ и контрольные точки

Диапазон индексов делится на блоки (`--batch-size`, по умолчанию 1000 страниц). Рабочие потоки независимо генерируют и анализируют блоки. Число выданных, но ещё не зафиксированных блоков ограничено `--queue-capacity` (по умолчанию 8). Готовые результаты хранятся по номеру блока; один писатель фиксирует их строго по порядку. Медленный ранний блок ограничивает выдачу новых работ, поэтому очередь не растёт вместе с длительностью сканирования.

Одна транзакция `commit_work()` включает находки, фрагменты, связи с предложениями, накопленные счётчики и контрольную точку. Записанный префикс диапазона всегда непрерывен. После аварии незавершённый блок можно вычислить повторно; его частично записанные результаты и счётчики не остаются. Уникальные ключи дополнительно защищают идентичность результатов.

Отмена прекращает выдачу новых блоков. Уже выданные блоки заканчиваются и записываются; это означает задержку остановки до завершения ограниченного окна работ. Исключение рабочего потока передаётся управляющему потоку, ожидающие потоки разблокируются, эксперимент получает статус ошибки. Время эксперимента накапливается между продолжениями.

`resume --pages N` добавляет `N` страниц начиная с сохранённого числа обработанных страниц. CLI восстанавливает конфигурацию v0.3 и сверяет отпечатки словаря, модели и POS-лексикона. Несовпадение параметров или содержимого входов вызывает ошибку. FNV-1a отпечатки предназначены для воспроизводимости, не для защиты от намеренной подмены. Конфигурации v0.1/v0.2 недостаточно полны для такого продолжения, поэтому для них требуется новый эксперимент.

## Хранилище

SQLite использует WAL, подготовленные запросы и пакетные транзакции. v3 расширяет существующую схему, сохраняя старые строки:

- `experiments`, `findings`, `checkpoints` — эксперимент, индивидуальные находки и записанный префикс диапазона;
- `passages` — исходный фрагмент, классификация, режим источника, компоненты связности и сведения о модели;
- `passage_sentences` — упорядоченные предложения с собственными адресами, смещениями, текстом и оценками;
- `pipeline_metrics` — накопленные счётчики стадий;
- `semantic_validations` — задел схемы для последующей интеграции семантической проверки.

Python-адаптер пока не записывает `semantic_validations`: он создаёт отдельный JSONL и файловый кэш. Наличие таблицы не означает, что проверка LLM выполнялась при сканировании.

Миграция запускается при открытии базы новым `Storage`. Чтобы сохранить старый архив побайтно, открывайте копию. Лаунчер v0.3 использует новую `data/bmm-v03.db`; старые пользовательские базы в ходе обновления не изменялись. `integrity` выполняет SQLite `PRAGMA integrity_check`.

Списки ограничиваются `limit`; экспорт читает результаты последовательно. Не следует одновременно запускать два задания продолжения одного эксперимента: распределённые аренды заданий и координация нескольких управляющих процессов не реализованы.

## Измерения

В `AnalysisMetrics` отдельно учитываются лексические совпадения, группы соседних слов, кандидаты предложений, принятие грамматикой, прохождение порогов и фрагменты. Время измеряется вокруг генерации, стадий анализа, ожидания окна и записи БД. Сумма времени параллельных стадий не равна общему wall time. Измерение транзакции не разделяет CPU SQLite, fsync и влияние внешних процессов. Фактические сравнения находятся в `EXPERIMENT_REPORT_V03.md`.

## Будущая интеграция с интерфейсом

Следующий слой может быть лёгким HTTP-сервисом над тем же ядром. Ему потребуется реестр заданий, сохраняющий объекты `Scanner`, и один владелец записи для каждой базы. Возможный контракт: создание задания, `GET` статуса/прогресса, запрос отмены, пагинация находок/фрагментов и потоковый экспорт. Числовой `experiment_id` — ключ сохранённых данных; идентификатор активного задания должен быть отдельным.

Progress callback можно передавать фронтенду через SSE или WebSocket. React или Tauri могут отображать список экспериментов, точные источники и отдельные оценки. Пагинация по устойчивому идентификатору, авторизация сервиса и согласованная отмена относятся к следующему слою. HTTP-сервис и графический интерфейс в v0.3 не реализованы.

`config/default.json` является справочным документом. Рабочие параметры задаются CLI/лаунчером и сохраняются в конфигурации эксперимента.
